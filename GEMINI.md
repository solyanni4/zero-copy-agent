# zero-copy-agent: Регламент маршрутизации и разработки для AI-агентов (Google Antigravity, Cursor, Cline)

Данный документ описывает правила выбора инструментов и стратегию выполнения задач при работе с репозиторием и интеграциями zero-copy-agent.

---

## 1. Правила выбора инструментов

При поступлении задачи агент обязан классифицировать ее объем и использовать соответствующий инструмент:

### Мелкие точечные правки (1 файл, до 20 строк)
* **Что входит:** исправление опечатки, замена константы, корректировка условия или флага, правка текста ошибки.
* **Как выполнять:** прямое редактирование файла через стандартные файловые инструменты (`edit_file`) без вызова сторонних цепочек и оркестратора.

### Средние задачи (1-2 файла, новый модуль или класс)
* **Что входит:** добавление новой функции, написание вспомогательного класса, парсера или валидатора.
* **Как выполнять:** связка локальной кодогенерации и облачного аудита:
  1. `local_gpu_code` — быстрая локальная генерация тела функции через Ollama (Qwen2.5-Coder 14B) на GPU с нулевыми затратами квот;
  2. `gemini_deep_analysis` — точечный аудит сгенерированного кода перед сохранением (проверка пограничных случаев и соответствия типам).

### Крупные многофайловые задачи (3+ файлов, новые подсистемы, рефакторинг)
* **Что входит:** разработка новых подсистем, переработка взаимодействия модулей, добавление сквозных фич с тестами, переписывание API.
* **Как выполнять:** через инструмент **`plan_and_execute_task`** (модель DAG-Planner + Local Worker + Final Integrator).
  * Параметры: `goal="<описание задачи>"`, `workspace_dir="."`, `resume=True`.

---

## 2. Архитектура DAG-Planner и чекпоинты (.zca/task_plan.json)

Крупные задачи не должны выполняться одной неконтролируемой портянкой кода. Модуль `plan_and_execute_task` реализует изолированный цикл:

1. **Декомпозитор (Архитектор):** облачная модель один раз строит направленный ациклический граф (DAG) из 3–7 атомарных шагов с явными контрактами и тестовыми командами проверки (`verification_cmd`).
2. **Контрольные точки:** план сохраняется в `.zca/task_plan.json`. Если во время работы прервалось сетевое соединение, исчерпался лимит или упал таймаут, повторный запуск с `resume=True` продолжает выполнение строго с первого незавершенного шага.
3. **Локальный воркер и контур защиты:**
   * Перед изменением файлов создается резервная копия через `history_manager`.
   * Локальная модель получает только контекст текущего шага и целевые файлы.
   * **AST-гейт:** синтаксическая валидация Python (`ast.parse`) / JSON / YAML.
   * **Test-гейт:** запуск `step.verification_cmd`. При сбое дается до 2 попыток исправления по тексту ошибки; если исправить не удалось — выполняется откат из бэкапа.
4. **Финальный интегратор:** общий прогон тестов (`pytest`) и аудит итогового `git diff` архитектором.

---

## 3. Требования к качеству кода

* Все новые модули должны сопровождаться unit-тестами в `tests/`.
* При любых правках запрещено удалять или модифицировать сторонние конфигурации пользователей.
* Версионирование синхронизируется через `core/version.py`, `config.yaml`, `core/updater.py` и `static/index.html`.
